## Summary

Integrate conversational AI capabilities into the Todo application, enabling users to manage all task operations through natural language conversation. The system uses OpenAI Agents SDK for intent interpretation, Model Context Protocol (MCP) server for stateless tool execution, and PostgreSQL for conversation state persistence. All components remain stateless with state reconstructed per request from the database.

**Key Technical Approach** (from research):
- **AI Agent**: OpenAI Agents SDK (lightweight, stateless orchestration)
- **Tool Layer**: MCP Python SDK (standardized tool interface)
- **Frontend**: OpenAI ChatKit (pre-built chat components)
- **State**: PostgreSQL tables (conversations, messages, tool_executions)
- **Rate Limiting**: Redis token bucket (per-user limits)

## Complexity Tracking

> **Justification for additions beyond Phase 2 baseline**

| Addition | Why Needed | Simpler Alternative Rejected Because |
|----------|------------|-------------------------------------|
| OpenAI Agents SDK | Required for natural language understanding and intent interpretation | Custom NLP insufficient for complex conversational patterns; would require months of training |
| MCP Server | Constitution mandates MCP architecture; provides standardized tool interface for AI agents | Direct function calls lack structure for AI discovery; REST API exists but MCP provides better agent integration |
| OpenAI ChatKit | Pre-built chat UI components reduce development time by ~60% | Custom React chat UI reinvents solved UX patterns (scrolling, typing indicators, message rendering) |
| Redis for Rate Limiting | Per-user rate limiting requires shared state across backend instances | Database-based rate limiting too slow; in-memory doesn't scale across instances |
| Conversation State Tables (3 new) | Stateless backend requires database-backed conversation history | In-memory state violates constitution; file storage lacks query capabilities for retrieval |
| Tool Execution Logging | Enables undo functionality and audit trail for AI actions | Without logging, users can't reverse AI mistakes; critical for trust and safety |
| Cleanup Scheduled Job | 30-day retention policy requires automated deletion | Manual cleanup not scalable; storage costs grow unbounded without automation |

**All additions deliver clear user value and comply with constitution requirements.**

## Architecture Decisions

### 1. AI Agent Framework: OpenAI Agents SDK

**Decision**: Use OpenAI Agents SDK for agent orchestration.

**Rationale**:
- Lightweight and focused on orchestration (not framework overhead)
- Native OpenAI function calling for tool selection
- Designed for stateless workflows (matches constitution)
- Simple agent-tool-handoff pattern fits our use case
- Better than LangChain (too complex, includes state management we don't want)

**Trade-offs**:
- ✅ Simple, stateless, good OpenAI integration
- ❌ Locked to OpenAI (not multi-provider like LangChain)
- Mitigation: MCP layer provides abstraction; can swap agents if needed

**Reference**: `research.md` - Technology Decision #1

### 2. Tool Architecture: Model Context Protocol (MCP)

**Decision**: Expose task operations through MCP server using Official Python SDK.

**Rationale**:
- Constitution mandates MCP architecture
- Standardized tool interface (works with any AI framework)
- Clean separation: tools don't know about agents, agents don't know about database
- Official SDK ensures compatibility and support

**Implementation**:
- 7 tools: `add_task`, `list_tasks`, `update_task`, `delete_task`, `mark_task_complete`, `search_tasks`, `bulk_delete_tasks`
- Each tool accepts `user_id` + parameters, performs database operation, returns structured result
- No state between calls; all context passed per invocation

**Trade-offs**:
- ✅ Framework-agnostic, standardized, constitution-compliant
- ❌ Additional abstraction layer vs direct function calls
- Benefit: Abstraction enables future agent swapping and external integrations

**Reference**: `research.md` - Technology Decision #2; `contracts/mcp-tools.yaml`

### 3. Conversation State: PostgreSQL Tables

**Decision**: Store conversations, messages, and tool executions in PostgreSQL.

**Rationale**:
- Already using PostgreSQL (Neon) for tasks
- ACID transactions ensure consistency
- Enables efficient queries (indexed by user_id, updated_at)
- Supports 30-day retention with scheduled cleanup
- No additional infrastructure (vs Redis/file storage)

**Schema**:
- `conversations`: Session metadata (user, title, active status, timestamps)
- `messages`: Individual messages (role, content, tool_calls JSON)
- `tool_executions`: Audit trail (tool name, parameters, result, status)

**Trade-offs**:
- ✅ Simple, consistent with existing architecture, ACID guarantees
- ❌ Slightly slower than Redis for reads (but < 100ms acceptable)
- Optimization: Index on `updated_at` for retention queries; limit context to last 20 messages

**Reference**: `data-model.md`; `research.md` - Technology Decision #4

### 4. Frontend Chat UI: OpenAI ChatKit

**Decision**: Use OpenAI ChatKit React component library.

**Rationale**:
- Pre-built components: MessageList, MessageInput, ChatContainer
- Handles common UX patterns (scrolling, typing indicators, formatting)
- Integrates well with Next.js 14 App Router
- Reduces development time by ~60% vs custom UI

**Trade-offs**:
- ✅ Fast implementation, proven UX patterns, official OpenAI library
- ❌ Less customization than building from scratch
- Mitigation: ChatKit is customizable; can extend/override components if needed

**Reference**: `research.md` - Technology Decision #3

### 5. Rate Limiting: Redis Token Bucket

**Decision**: Per-user rate limiting with Redis-backed token bucket.

**Rationale**:
- Prevents API abuse and controls OpenAI costs
- Token bucket allows burst requests while maintaining average rate
- Redis provides distributed state (works across multiple backend instances)
- Configurable limits (10 req/min default)

**Trade-offs**:
- ✅ Fair, distributed, burst-friendly, fast
- ❌ Requires Redis infrastructure
- Mitigation: Redis also useful for future caching; low operational overhead

**Reference**: `research.md` - Technology Decision #5

### 6. Conversation Retention: 30-Day Auto-Delete

**Decision**: Scheduled job (daily at 2 AM) deletes conversations older than 30 days.

**Rationale**:
- Manages storage costs (~100 KB per user per month)
- Privacy compliance (don't retain indefinitely)
- Cascading deletes clean up messages and tool_executions automatically

**Implementation**:
- APScheduler cron job in FastAPI app
- Query: `updated_at < (now - 30 days)`
- Batch delete in chunks of 100

**Trade-offs**:
- ✅ Automated, privacy-friendly, storage-efficient
- ❌ Users lose old conversations (could add export feature later)

**Reference**: `research.md` - Performance Considerations; `quickstart.md` - Step 9

### 7. Undo Functionality: Inverse Tool Execution

**Decision**: Track last tool execution; undo reverses it by calling inverse tool.

**Rationale**:
- Critical for user trust (AI might misinterpret intent)
- Audit trail already exists in `tool_executions` table
- Simple pattern: `add_task` → inverse is `delete_task`

**Implementation**:
- `/conversations/{id}/undo` endpoint
- Finds last successful tool execution (status=SUCCESS, order by `completed_at DESC`)
- Calls inverse tool with original parameters

**Limitations**:
- Only undoes last action (not full history)
- Some operations hard to reverse (e.g., bulk delete → restore all?)
- Mitigation: Ask for confirmation on destructive operations

**Reference**: `contracts/chat-api.yaml` - `/undo` endpoint

## Risk Assessment & Mitigation

### Risk 1: AI API Costs Exceed Budget

**Probability**: Medium | **Impact**: High

**Mitigation**:
- Strict per-user quotas (300 requests/month)
- Monthly cost monitoring dashboard
- Downgrade to GPT-3.5 if approaching limit
- Conversation truncation (last 20 messages only)

### Risk 2: Intent Parsing Accuracy < 90%

**Probability**: Medium | **Impact**: Medium

**Mitigation**:
- Extensive testing with sample conversations
- Clarification prompts for ambiguous input
- Undo functionality for misinterpretations
- Iterative agent instruction improvements

### Risk 3: Performance Degradation (> 2s response time)

**Probability**: Low | **Impact**: Medium

**Mitigation**:
- Streaming responses (perceive as faster)
- Conversation history truncation
- Database connection pooling
- Redis caching for user context

### Risk 4: OpenAI API Unavailability

**Probability**: Low | **Impact**: High

**Mitigation**:
- Clear error messaging to users
- Graceful degradation (suggest using traditional UI)
- Future: Consider multi-provider strategy (add fallback model)

### Risk 5: Database Storage Growth

**Probability**: Medium | **Impact**: Low

**Mitigation**:
- 30-day auto-deletion enforced
- Monitoring for storage trends
- Archival strategy if needed (export old conversations to S3)
